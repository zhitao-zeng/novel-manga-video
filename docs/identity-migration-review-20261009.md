# 身份归一迁移评审与建议(2026-10-09)

对 identity-auto-closure 设计(当前流程 vs 目标流程两张图)的详细评审。结论:**方向正确,可以走;
但有四条防线必须在目标态原样保住,且迁移顺序建议试点先行。** 本文每条都给出可验证的判据。

## 一、目标态里必须保住的既有防线

这些不是设计偏好,全是事故换来的(括号内是事故与机制位置):

1. **逐字证据纪律**。台账合并/采用决策必须带能在原文定位的引句(`entities/evidence.py` 的 span 定位)。
   目标流程里"修订候选 → 核对并采用"这一环,没有原文证据的候选不得进台账。
   判据:任何一条 same_as/合并记录都能点回原文句子。
2. **变身/乔装不自动合并**(`entities/contracts.py` 的 transformation 护栏,许流年案)。
   证据含"变成/乔装/假扮"而无"同一人"直陈 → 必须转人工,agent 不得自判自采。
   判据:护栏测试在目标路径上仍绿;构造一条变身证据走新流程,必须停在人工队列。
3. **人工裁决与模型产出分离存放、重读时重放**(`corrections.json` + `_correction_for`)。
   目标态若改存储,这条等价物必须在:重跑读书/解析不得冲掉人工结论。
   判据:光明纪元现有 239 条人工裁决在迁移后全部仍然生效(逐条 diff)。
4. **绑不上就卡章**(`story/source_identity.py` 的 active_cast_names 快速失败)。
   目标流程"复用已确认事实,增量处理本章新信息"之后,未确认的新指称仍要当场拦停,
   不得"尽力解析"后放给下游。今天的 ch221("门外的人")就是靠这条拦住的;
   现在有了 chapter_aliases(0b9996a),这类章内指称有了正规落点,更不该放行到下游。
   判据:构造一个全书未登记的新指称,规划必须在绑定阶段失败,而不是产出带 UNKNOWN 的分镜。

## 二、迁移顺序与窗口

1. **先试点:shiri(十日终焉)**。理由:300 章已全规划、身份数据干净、两起著名事故
   (许流年变身、地牛播种缺失)都在它身上,是最好的回归样本;且已收官,不在产。
   验收:全 300 章在新身份源下重新绑定,与现有绑定 diff —— 预期零变化(除已知修正);
   不触发任何付费重生成(绑定变化不影响已出资产)。
2. **再动光明纪元,且等 133 集恢复收尾之后**。它正在产,台账刚被人工复核过
   (6 条旧合并撤销、239 条裁决),是新流程最好的输入,也是最差的实验场。
   验收:239 条 corrections 重放一致;6 对被撤销的合并保持分离;既有绑定缓存口径不变
   或一次性全量重绑且不产生资产重生成。
3. **新书直接按目标态接入**,作为最终形态验证。

## 三、设计图里需要补明确的三个点

1. **别名归口**。今天别名有两处:`bible_aliases.json` 和 `reading_cast.json` 的 aliases,
   再加刚落地的 `chapter_aliases`。目标态"名单是导出视图"之后,别名写入口只能有一个
   (台账的实体 forms + 章级别名),两个旧文件变成同一份台账数据的导出。
   注意 `identity/store.py` 的缓存键含这两个文件——产出方变化会触发全量重绑,
   这是预期内的一次性成本,但要在迁移说明里写明,避免被当成回归。
2. **judge_unknown 的落点**。它现在把判决写进 `reading_cast.json`(declined/characters)。
   目标态下判决应写台账,名单由导出产生。这个写入点是"名单还是独立文件"的最后残留。
3. **归并 Agent 处理后续疑点的成本控制**。疑点驱动补读是好事,但要有预算上限
   (每章疑点数、每疑点补读章数),否则一个写岔的名字能引发全书重读。
   建议复用 `asked.json` 的"同一问题只问一次"机制做幂等。

## 四、性能红线

settle 索引(每实体章节列表 + 内存 mentions)今天刚落地,把 23 万次文件读降到零新增 IO。
目标流程的"共用解析"不得退回逐对全扫:任何"核对采用"路径的复杂度都应限于相关章节。
判据:光明纪元(799 章)全量身份复核 < 10 分钟完成。

## 五、不建议做的

- 不在光明纪元在产期间切换它的身份源(见二.2)。
- 不把绑定算法(连通分量、UNKNOWN 卡章)一起重写——它是被事故验证最多的部分。
- 不在目标态里引入新的存储引擎/图库——JSON 事件文件 + 派生视图在这个规模(600 实体)是可审计优势。

## 六、最小验收清单(试点收工判据)

1. shiri 300 章重绑 diff 为零(或逐条可解释);
2. 四条防线的判据测试全绿;
3. 一次端到端疑点处理演示:人为构造一个"ch221 门外的人"式指称,走 疑点→补读→核对→采用→重绑 全程,不产生人工干预;
4. 性能红线达标;
5. 回归:全量测试绿,且 `tests/fixtures/runtime_config_before.json` 等夹具口径同步。
