# 光明纪元：154条经验引用复盘

这次复盘来自85个恢复任务的 `current-task.json`：77个任务引用了154条历史案例，对应31个不同案例。31个案例都保存了正式 `final-candidate/manifest.json` 的通过回执；这是历史成片验收证据，不证明其中每次尝试有效，也不证明后来改过输入的主目录仍可直接交付。

审计原件和154条引用映射保存在本书恢复目录的 `memory-154-original-cases.json`。原有 `.production-memory` 案例、视频、素材与额度全部保留。

## 为什么经验没有充分发挥作用

旧摘要只把案例最后一次操作的前500字符传给Agent。154条引用全都只剩 `finish / ok=true / changed=[] / remedies=[]`。原记录中28个案例还有具体尝试细节，但有效操作和失败原因都没有传进去。

另一个限制是每个memory仅保留最近8次操作。479、528、623等案例的早期输入修改已从短memory中滑出；本次根据正式修复回执和 `repair_history/history.json` 补充说明。747只有固定流水线记录，764的素材提案被拒绝，不能替它们编造一条成功内容修法。623和747的最后收尾还涉及已经独立验证的ASR合成交接修复，见 `asr-assembly-handoff-20261008.md`。

## 本次修正与验证边界

- `recall`保留相关问题细节和memory仍持有的操作记录；任务提示词提炼实际changed/accepted片段、对应修法和失败原因，不再只截取最后finish。
- 一批apply的 `ok=false` 不抹掉其他片段已生效的修改；同一片段仍出现在blocked时，不把其候选当成有效经验。
- `changed`只证明操作生效，`accepted_clip`表示独立复核通过；整集outcome仍单独保留。unresolved不升级为成功。
- 短摘要最多3条问题、3条生效操作和2条失败尝试；具体input/edit/retake优先于大批keep。原始记录继续作为追溯入口。
- 新写出的memory Markdown也包含修法摘要与失败尝试。原始历史案例没有被覆盖；本次汇总保存在其独立summaries目录。
- 后续recall会按原memory文件名读取该书summaries中的人工复盘，传递具体案例结论及限制；历史复盘不会覆盖当前outcome，也不会替缺失的工具回执编造操作成功。

回归验证和85任务重放验证的是经验交接内容，不能据此声称剩余影片已修复或生成效果已改善。
