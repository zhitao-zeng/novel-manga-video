# Agent 接管最终请求修复

## 运行方式

小说 `profile.json` 选择 `repair_backend: sandbox_agent` 后，现有 managed 修复入口在首次失败时将证据交给现有 Docker 沙箱执行器。没有选择此后端的书保持当前执行方式，不改变 SD 或其他书的运行配置。

agent 看原文区段、目标及相邻分镜、当前英文请求、实际图片/音频、当前失败视频及最多三份历史视频、ASR和审查/修复记录。证据复制到现有 runs_root；容器只挂载本次运行目录，不挂生产目录。使用仓库 skills/video-repair/SKILL.md。每次最多600秒，输出decision.json及可选prompt.txt。

四种决定：edit提交完整英文；retake建议换seed；keep交给现有原文复核独立确认，不直接相信agent放行；stop报告无可支持的修法。每次agent只能提出一次候选，代码拒绝后不会再盲走旧修复路线。

## 与原流程的交接

- 首次失败由agent替代原有诊断/修段决策，不先消耗一轮旧修复。
- agent后端的语音失败不在渲染器内自行修正重试；额外语音和漏对白均进入现有审查反馈，由agent结合画面统一决策。
- 保留现有生成次数上限和修复历史。额度耗尽时不启动agent，也不会新增视频任务。
- 接受edit前保护六段结构、人物/素材定义及保留关系、精确对白、S/Audio绑定、镜数和时间标记，运行现有最终请求检查和实际参考图一致性检查。
- source、plan或feedback在沙箱运行时被其他任务修改，拒绝覆盖。
- 候选通过后使用现有RepairProposal与发布写回，保存agent来源和理由；不运行再次翻译覆盖其英文，不再进行单卡改写。真实渲染仍由原runner执行和计费。
- 同输入重新打包保留有效agent请求；源文本、镜头关联或编译输入改变时失效，不把旧修正强套到新镜头。

## 纯语音纠正

NOTE_ASK同时支持画面和语音修正，不再要求所有纠正必须描述画面。当模型将纠正并入镜头返回时，单独保留纠正声明，避免音频要求丢失后仍标记为已合并。“输入只是制作说明，无法生成画面描述”这一实际错误返回会被拒绝，不能当H3指令发送。
