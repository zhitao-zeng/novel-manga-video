# 准备与生成审修分别计时

用户确认的边界：准备包含源文/身份与输入修复、人物/场景/表情素材、请求翻译和提交前检查；完整素材及提交检查就绪后才开始生成审修活动预算。首次实际分镜提交前切换一次，后续补拍、语音/画面审核、合成和验收均消耗该阶段剩余时间。

新活动的 `timeout_seconds`（或 CLI `--timeout`）作为生成审修上限；准备默认沿用相同时长，可用任务配置 `preparation_timeout_seconds` 单独指定。现有默认值为两个阶段各 5400 秒，不改变任何模型路由、拍摄次数上限或质量门。

`agent-run.json.phase_budget` 保留当前阶段、两阶段上限和累计已用秒数，以及阶段开始/结束时间。外层 `deadline/remaining_seconds` 仍是当前阶段的既有投影，CLI、调度与工具继续读取它。共享资源等待沿既有区间合并扣除，不重复扣或重复返还。

切换接在现有 provider `before_video_submit` 中，先完成原提交检查，再开始生成时钟。因而 `render` 入口内补建表情图仍计入准备；准备不足不会启动一个新的生成预算。两名工作线程同时提交也只切换一次。已经有实际 take/在途任务的新审修宿主直接归生成审修阶段。

同一阶段的重启、配置变化和 `--retry-issues` 都不重新获得完整额度。任务已停止或让出资源时，接续只恢复已记录的剩余秒数，等待用户确认的空闲时间不扣活动预算；未经收尾的崩溃仍沿原截止时间保守恢复。显式有来源证据的旧恢复授权仍沿既有流程记账。原模型调用和每段生成次数不变。

旧 run 没有阶段记录时仍沿原单一时钟运行，不凭更新代码自动获得另一个预算。要按新口径接续，必须用它实际保存的准备/首个提交/停止记录归类已用时间，保留原状态和依据；不能按“现在重新开始”计为零。傲世22的历史18个take、5段语音失败和原规划账继续保留。

这次修改验证计时和恢复语义，不把已有失败视频重新标成通过。真实成片仍须正常内容与技术验收。
