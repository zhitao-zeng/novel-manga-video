# 每章选项、状态查询与渲染重试 · 2026-09-17

本轮落实三个后续点：消除整批共享选项的临时改写，分开状态读取和生产推进，独立片段重试决策。继续使用原有命令、产物格式、队列、锁、修复历史和预算。

## 每章选项

`Batch.plan(chapter, replan=..., notes=...)` 显式接收本章覆盖值。普通调用沿用启动参数和用户备注；拒绝后重规划只给当前章传覆盖值。

修正了两个实际问题：并行章节不再读到另一章临时打开的重规划开关；处理结束时不再把用户原本的重规划开关强制设为 false，也不再删除原有章节备注。失败时仍只失效本章旧计划，其他章节不受影响。

## 状态查询与生产推进

- `repair_manager_state_thin.read_snapshot` 读取并返回 `ManagerSnapshot`，不修改管理器对象、审查文件、历史或成片。
- 查询和推进共用准备资格检查、章节读取、状态判断和汇总；无需维护两套交付口径。
- `repair_manager_progression_thin.advance` 是管理循环显式调用的推进步骤。每章仍按“合并审查写回 → 观察修复历史 → 发布合格候选 → 读取发布后状态”的顺序处理，再更新管理器内存状态。
- 忙碌章节不写回，未完成开拍准备的章节仍归准备流程所有；单章不可读继续逐章容错。
- 管理循环仍在原位置保存状态。`progress` 命令继续导出原有诊断报告，但不写回生产审查、历史或视频。

## 渲染重试

`media/retries.py` 负责选择拒绝后的处理步骤、质量失败后的尝试和缓存检查，以及失败时如何保留已有素材。`render_attempt_thin.py` 执行一次生成或一个已选定的修复动作；`ThinMediaRunner` 负责串联并记录结果。

保留以下区别：

- 网络提交重试仍归供应商实现；不会把提交不确定当作可任意重发的请求。
- 修卡、软化请求、改写请求和输出拒绝后的处理仍使用原先的优先顺序与次数限制。
- 缓存失败、实际新生成和整集执行使用各自原有计数，不合并预算。
- 只有原逻辑需要时才查询后续缓存；失败之后继续保留已有可用素材。`cache-only` 缺失仍报告错误。
- 私有运行标记、实际请求、尝试记录、选择结果及最终报告格式不变。
