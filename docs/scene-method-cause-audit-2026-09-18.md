# 分场与导演实验：原因复核

结论：已确认本地引用契约、导演时长输入和修订方式存在问题；当前模型在这些请求下也有执行不稳，但没有隔离变量的模型对照，不能判定 Qwen 能力不足是主要原因。此次只读已有请求和返回、验证文字归属，并纠正报告；未调用模型或修改生产代码。

## 1. Drama 引文没有编造，原报告结论撤回

两次输出的 SC005-U02 引文在完整原文中均可连续匹配（按现有 quote_key 忽略标点和空白），但前半属于 seg_7、后半属于 seg_8。模型标了 seg_8；scenes.source_refs 只在每个区段内找完整引用，随后又按唯一 source_segment_id 过滤，最终报“引文不在完整原文中”。

证据：final-six/drama/response_01.json、response_02.json、common-payload.json 和 source.txt。两次检测均为 full_source=True、declared_segment=False。此前据失败文案认定“原文中没有这句话”是错误诊断。

修复方向：完整原文中的连续引用应能映射到多个已有区段；确实不在原文与仅定位不一致必须分开。无需允许虚构引用或模糊匹配。

## 2. 导演没有收到代码采用的台词估时

造梦师和 Visual 的第二次导演稿均把结尾台词分成 64 字、58 字两组，各计划 12 秒；代码按“1 秒起始 + 字数/4 + 每条台词 1 秒”算成 20 秒、18.5 秒，超过 15 秒上限。输入台词只含文字和编号，没有逐条时长、分组预算或这套公式。返回一次 37.5 秒超限反馈后，模型确实拆了镜，但仍未满足未显式提供的计算规则。

模型估时不准确是事实；本地把可确定计算的工作留给模型猜，也是接口缺陷。上游结尾共有 140 字对白，进入导演后禁止删改，进一步限制了下游压缩空间。

修复方向：用同一估时实现提供台词预算与可行分组；导演决定表演、镜头和停顿。仅末场分配出错时，只修改该场，不再重写整份导演 JSON。

## 3. 编剧修订过于依赖模型理解自由文本

社区/Leos 将吃兔肉、哭泣和次晨醒来混在一场。首次审查的 repair 同时允许“拆成两场”或“在正文单元前标次日”，而场景契约要求一个连续时空；返回只把场景时间从夜晚改成傍晚，没有拆开正文。

目前编剧修订仍使用完整写稿请求，只把旧稿和自由文本意见放入 revision，没有专门的受影响场景拆分操作。源复核、修稿和导演使用同一个配置模型；审查也有未充分依据原文推断衣服已干等问题。引用编号真实，并不自动证明审查结论真实。

修复方向：对已确认的问题给出明确、局部的修订任务；需拆场时更新场次与转场，不接受只改标签。审查结论仍需对照实际原文，不把更高拦截率当作更高质量。

## 4. 当前结果不足以归因模型能力

最终六路所有请求均为 Qwen3.8-27B-Project、enable_thinking=False。没有在相同输入与同等输出预算下获得另一个模型或推理模式的完整对照结果。早先开启思考的单次试探被 token 上限截断，不能代替有效对照。

社区与 Leos 的第一次编剧请求完全一致；四个方向类方法共用编剧步骤。本轮四路未进入方法导演，因此 0/6 是整条实现的完成率，混合了本地接口阻挡、写稿问题和模型判断，不能称为六种 Skill 的质量或 Qwen 的能力上限。

先修已证实的本地缺陷，再用固定失败场景做小规模同源对照，才有依据决定是否换模型。完整原文→分场→导演→H3 的职责划分可以保留，无需重做整个项目架构。
