# 身份减账一期：目标态与迁移三步（2026-10-08）

一期只落对账与目标态记录，不改在产结构。本文说明最终要去哪里、分三步怎么走、
每步怎么退，以及为什么现在只做一期。

## 现状：存在性记在三处

同一本书"有谁"目前由三份数据分别记录，彼此靠人工纪律维持一致：

- `story_bible.json` 的人物表：既存外貌设计（演员卡），也被当成存在性依据——
  台账从它播种（`ledger_store.seed_entities`，`source: "bible"`）。
- `reading_cast.json` 的名单：由归并独立产出（`planning/initialize.py` 的
  `--cast` 落盘，`lean_reading.py` 的 MERGE_PROMPT），`flow.py` 的
  `reading_aliases` 还从它读别名。
- `entity/` 台账（`entities.json` / `claims.json` / `types.json`）：逐章读书
  追加实体与证据，是绑定实际沿用的身份图。

三处不一致的代价已经付过：初始台账只从初始圣经播种，圣经后来长出来的人不会
自动进台账，绑定沿别名走到空处、章节卡死（十日终焉 2026-09-29，地牛案例）；
归并误并则让两个源角色落到同一行（雾月误并案例）。减账的方向是把存在性收敛
到一处，另外两处退化为派生物。

## 目标态

- **台账 `entity/` 是存在性的唯一事实源。** 谁在这本书里存在、别名指向谁、
  合并依据哪条证据，只查台账。
- **名单是台账的视图，不是独立维护的文件。** `reading_cast.json` 的内容等于
  台账 named 实体（含别名映射）的一次导出；需要它的消费方照读这个导出，没有
  人再去"维护名单"。
- **圣经 `story_bible.json` 只存外貌设计，不存存在性。** 它回答"这个人长什么
  样、穿什么"，不回答"这本书有没有这个人"。台账播种不再以圣经人物表为准；
  圣经引用台账实体来挂设计。

## 迁移三步

### ① setup/reconcile 对账（已在位）

名单与台账逐项核对，差异显式暴露而不是默默发散：

- 新书接入第 5 步：`scripts/setup_book_thin.py` 的"名单 vs 台账对账"，为名单
  中台账缺失的人播种 named 实体（只播种"存在"，外貌仍由读书逐章补；指称别名
  不播种，避免污染台账）。
- 独立复核入口：`scripts/reconcile_cast_ledger.py --novel-dir outputs/X [--fix]`。
  `--fix` 只补"名单在册、台账无实体"一类；变身/乔装类证据支撑的 `same_as`
  合并只列待复核清单，必须人工裁决，脚本不自动撤销。

回退：对账是附加检查，删掉 setup 第 5 步和不跑 reconcile 即回到原状；已播种
的实体在台账里是普通 named 实体，手工从 `entity/entities.json` 移除对应行即可。

### ② 新书 reading_cast 改为由台账生成

归并不再独立产出名单文件；归并结果写入台账（实体 + 别名 + same_as 证据），
`reading_cast.json` 改为从台账 named 实体导出的视图，供 `flow.py` 的别名读取、
`initialize.py --fill` 的覆盖判断等现有消费方原样使用。归并规则本身（一人一
实体、共现不是同指）不变，变的只是落点。

回退：导出是纯函数，台账不动；恢复旧路径即让 `initialize.py` 重新直接写
`reading_cast.json`，与台账并存——这正是今天的现状，无数据迁移成本。

### ③ 旧书逐步并轨

在产旧书逐本跑 `reconcile_cast_ledger.py`：先 `--fix` 播种缺口，再人工裁决
变身类合并清单，确认该书名单与台账一致后，该书转入"台账为准"模式。一次只并
一本，并完观察至少一集完整生产再并下一本。

回退：单书粒度。某本书并轨后出问题，恢复该书备份的 `reading_cast.json` 与
`entity/`（并轨前整目录留档），其余书不受影响。

## 为什么现在只做一期

feat/episode-agent 是在产分支，在产书籍的章节绑定缓存以
`story_bible.json`、`bible_aliases.json`、`reading_cast.json`、`entity/` 等
文件的签名做缓存键（`identity/store.py` 的 `data_files`）。第 ② 步改变
reading_cast 的产出方，第 ③ 步改变旧书的数据形态，二者都会让在产书的既有
绑定缓存与已验收产物面临重算口径变化——这不是代码对错问题，是在产数据迁移
问题，必须按书、按窗口做，不能随分支改动一次性生效。

所以一期只做：把对账钉死在 setup（已完成）、把目标态与迁移路径写成文档（本文）。
② ③ 各自独立成期，各自带回退，不与本期捆绑。
